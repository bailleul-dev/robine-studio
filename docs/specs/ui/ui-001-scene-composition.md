# UI-001: Scene projection and visual composition

Status: Draft

## Summary

Robine UI projects semantic equipment instances into interactive visual scenes.
Product developers describe equipment through MOD-001 to MOD-003; they do not
author the scene hierarchy or place controls at screen coordinates.

Visual recipes describe how catalog parts look. The projection system combines
those recipes with solved assembly transforms, connectivity, articulation state,
camera state, parameters, and selection state to produce a renderable scene.

## Goals

- Generate scenes from semantic equipment and assembly descriptions.
- Compose visually rich parts from interchangeable geometry and materials.
- Show exterior, interior, exploded, wiring, and rig views of the same instance.
- Reuse geometry, materials, interactions, and bindings independently.
- Support both plugin-embedded and standalone rendering.
- Permit model, recipe, and asset hot reload without losing valid instance state.

## Non-goals

- Making scene nodes the product-authoring API.
- General desktop forms, document editing, or arbitrary application widgets.
- A CSS or browser-compatible layout engine.
- Encoding electrical connectivity or DSP behavior in visual recipes.

## Projection inputs

A scene projection receives:

- A validated MOD-001 runtime equipment instance.
- Solved mechanical transforms from MOD-002.
- Connectivity and route presentation data from MOD-003.
- Current core parameter values.
- A view mode, camera, focus target, and inspection filters.
- A catalog of visual recipes, geometry, materials, decals, and fonts.

The projection output is disposable. Destroying or rebuilding it MUST NOT destroy
equipment, connection, replacement, parameter, or articulation state.

## Generated scene model

The runtime scene is a retained hierarchy generated by the projection system.
Each node contains:

- A stable derived ID linked to an equipment role or generated visual role.
- A parent-relative 3D transform and physical bounds.
- Optional 2D overlay or label constraints.
- Ordered geometry and material components.
- Optional interaction behavior and semantic action target.
- Optional core parameter binding.
- Visibility, opacity, clipping, selection, and enabled state.

Nodes may represent an enclosure, lid, control, jack, PCB, electronic component,
speaker, microphone, wire, cable, label, or purely decorative layer. High-level
objects expand into reusable renderer primitives; the renderer itself contains no
product-specific behavior.

## Visual recipes

Catalog parts reference visual recipes. A recipe may combine:

- Procedural or imported geometry.
- One or more reusable materials.
- Decals, engraved text, wear masks, and labels.
- Articulation visualization and selection affordances.
- Named visual slots for compatible subparts.

A knob recipe can combine body, cap, skirt, indicator, tick scale, material, and
shadow treatment. Adding a body shape or material MUST NOT duplicate the complete
knob. Runtime rotation MUST NOT depend on a strip of pre-rendered value images.

Recipes support named slots and explicit local overrides. Deep visual inheritance
chains SHOULD be avoided in favor of composition and small shared style tokens.

## Views and cameras

The same generated scene supports:

- Front, rear, top, underside, and interior presets.
- Closed, articulated-open, removed-panel, and exploded states.
- Orbit, pan, zoom, focus, and frame-selection operations.
- Orthographic equipment views and perspective inspection views.
- Optional connectivity overlays and isolation of selected subassemblies.

Opening a pedal changes its MOD-002 articulation state and regenerates or updates
the affected scene nodes. It MUST NOT switch to an independently authored
interior UI.

## Screen-space composition

Physical objects are projected from millimetre-based model space. Screen-space UI
uses logical units independent of physical pixels for labels, value popovers,
selection outlines, tooltips, and Studio-only inspection chrome.

- Overlay anchors derive from projected semantic attachment points.
- Labels use collision-aware placement around their target.
- Pixel snapping is opt-in for screen-space elements that require it.
- Controls and inspection affordances remain usable from 75% through 200% UI
  scale.

Product descriptions MUST NOT provide screen-space coordinates. Visual recipe
authors MAY define geometry in a catalog part's encapsulated local frame.

## Physical scale discipline

All scene geometry is solved from one physical coordinate system. Catalog
dimensions remain authoritative in millimetres; the current renderer maps 200 mm
to one world unit only at the projection boundary. Cameras and lights may use
artistic placement, but they MUST NOT compensate for incorrectly scaled objects.

The reference scene locks representative measurements: a generic single pedal is
70 x 122 x 55 mm, the reference combo is 620 x 500 x 260 mm, and the studio is
approximately 8.4 x 7.2 x 3.2 m. Hardware such as knobs, footswitches, LEDs,
jacks, floor boards, wall lights, and acoustic panels uses the same conversion.
Changing the world-unit conversion MUST therefore preserve every ratio rather
than resizing enclosure bodies alone.

## Compilation and updates

Projection resolves equipment roles, assembly transforms, material and geometry
handles, core parameter IDs, semantic actions, traversal order, and hit-test
metadata.

It MUST reject:

- Equipment roles without required visual recipes.
- Duplicate derived node IDs.
- Missing visual slots or assets.
- Unknown parameter bindings or semantic actions.
- Non-finite transforms or invalid physical bounds.

Hot reload compiles replacements before publication. Failure leaves the previous
valid projection and resources active and reports diagnostics against semantic
equipment roles or catalog recipes.

## Acceptance criteria

- A complete pedal scene is generated without product-authored scene nodes or
  render coordinates.
- One pedal instance can be viewed closed, open, upside down, and exploded.
- The exterior and interior views share the same equipment and connection state.
- One knob body combines with at least three skirts or indicators without
  duplicated control implementations.
- A pedal moved on a board updates attached visual cables without changing the
  connection graph.
- A scene can be discarded and regenerated without losing instance state.
- Invalid projection references produce semantic, source-oriented diagnostics.
- Pedal, amplifier, room, and hardware ratios remain invariant when projection
  scale changes.
